# NL2SQL 项目测试框架（简化版）

> 针对本项目实际环境定制。本项目只有两个环境：**本地开发**和**服务器**。
> 版本：v2.0 日期：2026-09-08
> 对应评测脚本：`scripts/eval_accuracy.py`（130 条可执行用例）
> 对应用例集：`docs/spec/M7_评测用例集.md`（150 条，JOIN 20 条待造数）

---

## 一、测试环境

本项目只有两个环境，没有 CI/CD 流水线、没有预发布/灰度环境。

| 环境 | 地址 | 配置 | 用途 |
| :--- | :--- | :--- | :--- |
| **本地** | `localhost:8080` | Windows + JDK 17 + Maven | 代码开发、单元测试、Mock 调试 |
| **服务器** | `<ECS公网IP>`（阿里云 ECS 2核2G） | Ubuntu 22.04 + MySQL 8.0 Docker + JDK 17 + nginx | 全量评测在此跑（唯一有真实 LLM API 的环境） |

### 环境隔离三原则

1. **数据隔离**：测试数据库独立实例，禁止跨环境共享。本项目 orders 表通过 Flyway V1 迁移初始化。
2. **状态隔离**：每个用例执行前重置 Agent 状态（清缓存、清对话历史）。
3. **网络隔离**：服务器有密码，AI 不可直连。所有服务器操作由用户手动 SSH 执行。

## 七、LLM-Judge 校准规范

使用 LLM 评估 LLM 时，需进行校准以保证公平：

- **Prompt 模板**：提供明确的评分标准（如：SQL 逻辑等价得 1 分，字段错误扣 0.5 分）
- **一致性测试**：使用已知结果的数据测试 Judge 模型，如果评分与人工评分一致性低于 80%，需调整 Judge Prompt
- **80% 阈值依据**：LLM-Judge 文献中的经验下限，低于此值说明 Judge 模型能力不足或 Prompt 不够清晰
- **执行级验证优先**：纯 LLM 文本比对存在误判风险，优先使用**执行级逻辑验证**——在测试库分别执行生成 SQL 和标准 SQL，结果集一致则逻辑正确

## 八、幻觉检测自动化方案

### Schema 幻觉检测
1. 编写脚本解析生成的 SQL，用 JSqlParser 提取所有表名和字段名
2. 与数据库 `information_schema` 进行比对
3. 不存在的表/字段即为 Schema 幻觉

### 数值幻觉检测
1. 将 LLM 回答中的关键数字提取出来
2. 与 SQL 执行结果的聚合值进行比对
3. 误差超过 5% 视为数值幻觉

### 逻辑幻觉检测
1. 回答了但答非所问（如"我不知道"或胡言乱语）
2. 已合并到幻觉率子类，不再单列

| 指标 | 对应代码 | 怎么从代码里拿数据 |
| :--- | :--- | :--- |
| SQL 生成准确率 | `QueryService.query()` → `generatedSql` | 评测脚本断言 `data.sql` 包含关键词 |

| 端到端延迟 | `QueryService.query()` → `latencyMs` | 评测脚本从 `data.latencyMs` 取值排序计算分位数 |
| 环节延迟拆分 | `LangfuseObservability.record()` → OTel span | Langfuse Dashboard 按 span 名称筛选 |

| 并发隔离率 | `UserContext`（ThreadLocal）+ `SemanticCache`（key 含 role） | 并发组验证各请求结果不串扰 |
| 自愈成功率 | `SelfCorrector.correct()` → 修正后重试 | 构造语法错误问题，统计修正后 code=2000 比率 |

| 审计日志完整率 | `AuditService.record()` → `audit_logs` 表 | 查表记录数 = 评测请求总数 |
| 链路追踪覆盖率 | `TraceIdFilter` + `LangfuseOtelTracer` | 检查响应头 traceId 非空 + Langfuse span 存在 |
| 缓存新鲜度达标率 | `SemanticCache` + 指标治理状态机 | 废弃指标后重复问，验证缓存不返回旧口径 |
| 治理状态隔离率 | `MetricMatcher`（WHERE status='published'）+ `MetricGovernanceService` | 废弃指标后问相关问题，验证不命中 deprecated 指标 |
| 单次问数成本 | `LlmUsage`（prompt_tokens + completion_tokens） | 从 LLM 响应提取 token 用量 × qwen-turbo 单价 |
| 幻觉率 | `SqlValidator` + `SqlExecutor` | 解析 SQL 表名/字段名比对 information_schema；数值结果比对 |

## 附录 A：技术选型评估（一次性，非持续监控）

| 方案 | 优势 | 劣势 | 成本 |
| :--- | :--- | :--- | :--- |
| **生成 SQL（本项目）** | 精确查询、口径可治理、权限可注入 | 依赖 LLM 质量、延迟较高 | 中等（qwen-turbo ~0.01元/次） |
| 直接 RAG 回答 | 快、简单 | 数值不可靠、无法聚合、口径不可控 | 低（向量检索 + LLM 总结） |

> 本项目选择"生成 SQL"方案，因为电商问数场景对数值准确性要求极高，RAG 方案无法保证聚合逻辑正确。
