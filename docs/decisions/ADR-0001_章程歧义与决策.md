## 已决项

### D-01 HikariCP 最大连接数

- **决策**：`maximum-pool-size = 10`（固定值，不再区分"生产可调至 20"）。
- **影响范围**：章程 §性能优化层、§风险与应对「连接池打满」行、§6.3 HikariCP 调优。
- **章程原文矛盾**：§性能优化层写 `10`（加注"生产可调至20"），§风险表写 `20`。

### D-02 置信度阈值与分级

- **决策**：置信度 `c` 分三级，行为如下：
  - `c ≥ 0.85` → 高置信，直接返回 SQL 给下游执行；
  - `0.60 ≤ c < 0.85` → 中置信，执行一次额外的 SQL 语义自检，通过则放行并在溯源中标"中置信"，不通过则转反问（方案 C）；
  - `c < 0.60` → 低置信，不执行 SQL，转反问澄清，二次确认意图。
- **影响范围**：章程 §置信度评估+反问澄清、§NL2SQL流程步骤 3/4、错误码 4002、评测指标「反问澄清准确率 ≥70%」。
- **注**：本项在 M3（置信度+澄清）里程碑生效，M1 不涉及。

### D-03 角色口径

- **决策**：
  - **系统角色（RBAC）** = 4 种：`admin / operator / product / manager`，决定数据范围与功能权限；
  - **团队角色（章程正文的"数据分析师 / 产品经理"）** = 组织分工，**不进入系统 RBAC**。
- **影响范围**：章程 §团队分工、§RBAC 权限体系、§指标口径管理。

### D-04 数据量

- **决策**：测试/生产数据量统一钉为 **150 万条（orders 表）**，不再使用"100–200 万"区间表述。
- **影响范围**：章程标题「数据规模」、§测试数据规模、§环境策略 staging/prod「150万」。

### D-05 中置信行为（对应原 U-01）

- **决策**：方案 C —— 中置信额外执行一次 SQL 语义自检，通过则放行并标记"中置信"，不通过则转反问。
- **理由**：贴合章程"不准时能告诉你它不准"的定位，不静默放行，也不过度打扰。
- **生效里程碑**：M3。

### D-06 语义缓存 key 追加 role（对应原 U-02）

- **决策**：语义缓存 key 由 `hash(question + schema_version)` 改为 `hash(question + schema_version + role)`。
- **理由**：缓存命中发生在权限注入之前，若 key 不含角色，运营 A 会命中管理员 B 缓存的全量结果，造成跨角色数据串读。追加 `role` 消除该洞。
- **生效里程碑**：M4（语义缓存引入时）。

### D-07 账号模型（对应原 U-03）

- **决策**：系统账号与 20 万业务用户分离，二者共存于 `users` 表：
  - `users` 表新增 `password_hash VARCHAR(100) NULL`（业务用户为 NULL）；
  - 新增 `is_system_account BOOLEAN NOT NULL DEFAULT false`；
  - 系统账号约 10 个，由独立初始化脚本创建（`is_system_account=true` 且 `password_hash` 非空）。
- **理由**：章程 `users` 表字段无密码字段，但 JWT 登录需要鉴权。业务用户是"被查询的数据"，系统账号是"能登录的账户"，二者职责不同。
- **生效里程碑**：M2（RBAC + 登录）正式启用；`users` 表结构 M2 的 Flyway 迁移建全。

### D-08 审批动作系统角色映射（对应原 U-04）

- **决策**：指标审批人（章程"产品经理"）映射到系统角色 **`admin`**（admin 具备"管理指标定义"权限）。
- **生效里程碑**：M2（指标语义层审批流）。

### D-09 AI 框架选型（M1 阶段）

- **决策**：M1 用 REST 直连 DashScope OpenAI 兼容端点（Spring `RestClient`），不引入 Spring AI Alibaba。
- **理由**：M1 仅需"生成一条 SQL"，Spring AI Alibaba 的 Agent/Graph 为过度设计，且引入模型元数据、连接池等非堆开销；M3 复审是否引入。
- **生效**：M1 起，M3 复审。
- **偏离章程**：章程技术栈表原写 Spring AI Alibaba（问数链），本决策为主动偏离并显式延后框架选型。

### D-10 双数据源（SR-2 只读连接的落地）

- **决策**：方案 A —— 显式定义两个 DataSource：主数据源（@Primary，读写）供 Flyway 迁移建表；只读数据源（`readOnly=true`）供 SqlExecutor 查询。
- **理由**：章程 SR-2 要求"MySQL 连接强制只读"，但 Flyway 建表是写操作，与单数据源 read-only 冲突。分离后：Flyway 用主库读写，查询用只读库，SR-2 不被降级。
- **生效**：M1。
- **实现**：`config/DataSourceConfig` 显式定义 `dataSource`(@Primary) + `readonlyDataSource`，`SqlExecutor` 注入 `@Qualifier("readonlyJdbcTemplate")`。
