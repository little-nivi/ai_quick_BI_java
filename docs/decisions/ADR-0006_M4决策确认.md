# ADR-0006 M4 决策与默认值确认

> 状态：已决（D-21~D-25 + P1 全部确认）
> 日期：2026-08-22
> 确认人：用户（"全部照单"）
> 上游依据：ADR-0001（D-06 缓存 key 含 role）、章程 §缓存抽象层设计、§降级与容灾

---

## D-21 语义缓存 key 含角色（正式启用 D-06）

- **决策**：语义缓存 key = `hash(question + schema_version + role)`，M4 正式落地。
- **理由**：缓存命中发生在权限注入之前，key 不含 role 会导致跨角色串读（运营 A 命中管理员 B 的全量结果）。ADR D-06 已定，此处确认启用。

## D-22 缓存范围（只做语义缓存 + 权限缓存）

- **决策**：M4 仅实现 **语义缓存**（question→结果，最有效）与 **权限缓存**（role→data_scope，变化极小）。
- **不做**：Schema 指纹缓存、查询缓存、会话缓存（这些留后续里程碑）。
- **理由**：单机 dev 环境，其余缓存收益低、复杂度高；语义缓存覆盖 80% 的重复查询收益。

## D-23 降级链顺序（方案 A，可测试）

- **决策**：M4 只实现可测试的降级链：模型 API 超时 → 查语义缓存该问题最近成功结果 → 仍无则返回友好提示。
- **不做**：降级到 qwen-plus（dev 无该模型 key，无法测试）。
- **理由**：避免硬编码无法测试的降级分支；多模型降级留 prod（有多模型环境）。

## D-24 会话写穿透（只落库，不做多轮）

- **决策**：M4 只把每次 Q&A 落库到 `session_records` 表（写穿透），不做真正的多轮上下文记忆。
- **理由**：真正的多轮会话需要 session 机制 + 上下文拼接，复杂度高；M3 反问是无状态的，M4 先落库记录，多轮留后续。

## D-25 CacheService 接口形态（通用 get/put/evict/clear）

- **决策**：接口精简为通用 `get/put/evict/clear`（带 TTL），不把 5 类缓存硬编码进接口方法；具体缓存用不同 cache name/实例区分。
- **理由**：加一种缓存不改接口；符合"接口可替换、可平滑迁移 Redis"的章程目标。
