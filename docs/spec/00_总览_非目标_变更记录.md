## 0. 本文档定位

本文档是项目 Spec 体系的**总索引 + 全局约定**，不承载具体业务规则。具体业务规则按里程碑拆分为独立 Spec 文件（见 §2），各文件遵守本文档的编号、错误码、术语约定。

## 1. 文档与代码的关系（追溯链）

```
章程(PRD) → ADR(人拍板) → Spec(REQ/TC，版本化) → 代码(引用 REQ) → 测试(引用 TC)
     ↑______________________________________________↓
           行为变更先改 Spec → 变更日志 → 重新生成代码
```

- 代码实现处注释/提交信息引用 `// REQ-<模块号>-<流水>`；
- 自动化测试用例名/注释引用 `TC-<模块号>-<流水>-<序号>`；
- 无 REQ 编号的代码视为脱离 Spec（SPEC_CODING_STANDARD §3）。

## 2. 文件组织（里程碑拆分）

标准 §8 建议按六大模块拆分文件；本项目为个人增量开发，采用**按里程碑拆分**，每份里程碑 Spec 内部按六大模块组织。理由：里程碑是功能增量的自然单位，小份 Spec 更易修订与二次生成。

## 3. 编号约定

- **REQ 编号**：`REQ-<模块号>-<流水>`，模块号取标准 §2 编号（1=业务目标，2=架构，3=数据模型，4=接口，5=核心逻辑，6=边界/验收）。
- **TC 编号**：`TC-<模块号>-<流水>-<序号>`，回链其验证的 REQ。
- **全局唯一性**：`<流水>` 在项目内**跨里程碑全局递增、永不重复**，由下表统一分配；已分配编号不得回收。

## 5. 术语

沿用 SPEC_CODING_STANDARD_v2 附录 B，另补：

| 术语 | 定义 |
|---|---|
| 问数 | 以自然语言提问并获取数据结果的意图 |
| 反问澄清 | 置信度不足时，系统向用户返回澄清问题以确认意图，而非直接执行 |
| 中置信 | 0.60 ≤ 置信度 < 0.85，执行额外语义自检后放行或转反问（见 ADR D-02/D-05） |
