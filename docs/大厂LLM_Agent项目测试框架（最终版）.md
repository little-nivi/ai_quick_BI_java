# 大厂 LLM Agent 项目测试框架（最终版）

## 一、 完整指标体系（七层）

### 第 1 层：功能质量层（答得对不对）—— 问数项目的核心层

| 指标 | 定义（无歧义） | 怎么测 |
| :--- | :--- | :--- |
| **SQL 生成准确率** | 生成的 SQL 语法正确且逻辑符合意图 ÷ 总条数 | 1. **语法检测**：用数据库 Explain 或 Linter 自动检测。<br>2. **逻辑比对**：用 LLM-Judge 对比生成的 SQL 与标准 SQL 的逻辑等价性。<br>3. **执行级逻辑验证**：对于无法通过文本比对确认的 SQL，在测试库中分别执行"生成的 SQL"和"标准 SQL"，若结果集一致（或高度重合），则视为逻辑正确。此方式比纯 LLM 文本判断更可靠。 |
| **答案准确率** | 最终返回给用户的数值/结论与标准答案一致 ÷ 总条数 | **执行级比对**：自动执行 SQL 获取结果，与评测集的标准结果进行数值比对。 |
| **意图识别准确率** | 用户问题被正确路由到对应意图（查数/闲聊/操作）÷ 总条数 | **评测集标注对比**：构建包含单轮和多轮追问的意图测试集，自动化跑分。 |
| **多轮意图准确率** | 在追问、澄清、话题切换场景下，正确识别意图 ÷ 多轮测试总数 | 构造多轮对话测试集（如："看下销量" -> "那华东区呢？"），验证上下文继承是否正确。 |
| **拒答正确率** | 权限外/敏感问题/非业务问题被**正确拒绝** ÷ 应拒绝总数 | 构造越权、竞品分析、政治敏感等"攻击性"用例集。 |
| **幻觉率** | 回答中编造了不存在的表/字段/数据 ÷ 总条数 | **拆解检测**：<br>1. **Schema 幻觉**：自动比对 SQL 中的表名/字段名是否存在于元数据中。<br>2. **数值幻觉**：比对 LLM 总结的数值与 SQL 执行结果是否一致。 |
| **失败率** | 系统报错（5xx/超时/解析失败）÷ 总请求 | 评测集全量回归统计。 |

> **电商问数特有重点**：
> *   **幻觉率**是红线。数据错了比不回答更严重，大厂会专门测"看似合理其实编造"的回答。
> *   **多轮准确率**是难点。需重点测试"省略主语"的追问场景（如"它的转化率是多少"）。

### 第 2 层：性能层（快不快）

| 指标 | 定义 | 怎么测 |
| :--- | :--- | :--- |
| **端到端延迟 (P50/P90/P99)** | 请求发出 → 响应返回的延迟分位数 | 使用 k6 或 JMeter 进行压测。 |
| **环节延迟拆分** | **（关键）** 意图识别耗时 / 检索耗时 / SQL生成耗时 / SQL执行耗时 / 答案总结耗时 | **链路埋点**：利用 Langfuse 或 SkyWalking，通过 TraceId 关联各环节时间戳。 |
| **首 Token 延迟** | 从发出请求到收到第一个字节的耗时（流式响应场景） | 压测脚本记录 Time To First Byte (TTFB)。 |
| **吞吐 QPS** | 每秒完成的问数请求数 | k6 压测。 |
| **缓存命中率 & 加速比** | 命中 ÷ (命中+未命中)；以及 命中P95 vs 未命中P95 的耗时对比 | 埋点计数 + 分组压测。 |
| **数据新鲜度达标率** | 查询结果的数据时间戳与当前系统时间的差值在规定阈值内（如 5 分钟）的请求占比 | 构造实时写入的测试数据，立即发起查询，计算 `当前时间 - 结果中最新数据的时间戳`，差值在阈值内即视为达标。 |

### 第 3 层：成本层（贵不贵）—— LLM 应用大厂必看

| 指标 | 定义 | 备注 |
| :--- | :--- | :--- |
| **单次问数成本 (Avg/P95)** | 一次完整问答的 LLM API 费用（输入+输出 token × 单价） | 增加 P95 成本，防止长尾请求拉高平均值。 |
| **环节成本拆分** | 意图识别成本 / SQL生成成本 / 答案总结成本 | 定位哪个环节最烧钱，针对性优化 Prompt。 |
| **Token 消耗比** | 平均每次问数消耗的输入/输出 token 数 | 监控 Prompt 是否过长。 |
| **缓存成本节约率** | (命中次数 × 单次平均成本) ÷ 总成本 | 量化缓存带来的直接金钱收益。 |
| **方案成本对比** | "生成 SQL 方案"成本 vs "直接 RAG 回答"成本 | 用于向业务方证明技术选型的经济性。 |
| **单次成本告警阈值** | **（新增）** P95 单次问数成本超过设定值（如 0.5 元）时触发告警 | 防止长尾请求导致成本失控，告警后需定位高消耗用例并优化。 |
| **月度预算上限** | **（新增）** 月度 LLM API 总费用超过设定值（如 Y 元）时触发限流 | 设定月度成本红线，超限时自动降级非核心请求或切换低价模型。 |

### 第 4 层：安全合规层（安不安全）—— 电商数据敏感，这层优先级最高

| 指标 | 定义 | 怎么测 |
| :--- | :--- | :--- |
| **越权拦截率** | 用户 A 试图查用户 B 的数据，被正确拦截 ÷ 攻击测试次数 | **硬指标：必须 100%**。构造跨部门、跨角色的攻击用例。 |
| **多轮越权拦截率** | 在多轮对话中，试图通过上下文绕过权限检查，被正确拦截 ÷ 攻击次数 | 构造"先问公开数据，再追问敏感数据"的诱导性多轮用例。 |
| **Data Scope 生效率** | 生成的 SQL 自动带上了正确的权限过滤条件（如 `dept_id = xxx`）÷ 总查询数 | 解析生成的 SQL 语句，正则匹配是否包含预期的权限过滤子句。 |
| **SQL 注入防护率** | 恶意输入（如 `'; DROP TABLE...`）被识别拦截或转义 ÷ 攻击用例数 | 使用 SQLMap 或手工构造注入 Payload 测试。 |
| **敏感字段脱敏率** | 手机号/身份证/金额等被正确脱敏（如 `138****1234`）÷ 应脱敏字段数 | 结果集正则校验。 |
| **审计日志完整率** | 每次问数（谁、何时、问了什么、看了什么、SQL是什么）都有记录 ÷ 总次数 | 数据库抽查日志表。 |

### 第 5 层：可靠性层（稳不稳）

| 指标 | 定义 | 备注 |
| :--- | :--- | :--- |
| **可用性 SLA** | 成功响应 ÷ 总请求（目标 99.9%+） | |
| **系统错误率** | **（合并）** 5xx + 超时 + 解析失败 ÷ 总请求 | 替代原有的"失败率"和"错误率"，统一定义。 |
| **降级成功率** | 缓存挂了/LLM 超时时，降级链路（如返回默认值、简化版回答）是否正常兜底 | 故障演练（Chaos Engineering）。 |

### 第 6 层：体验层（好不好用）

| 指标 | 定义 | 备注 |
| :--- | :--- | :--- |
| **回答可解释性** | 回答是否带数据来源、计算口径说明、SQL 展示 | 电商问数用户很在意"这个数哪来的"，需人工验收。 |
| **无效回答率** | 回答了但答非所问（如"我不知道"或胡言乱语）÷ 总条数 | |
| **多轮追问成功率** | "再按华东分一下"这类追问是否正确继承上下文并返回正确结果 | |
| **回复内容合规率** | 回答中不包含敏感词、政治风险、竞品引导等违规内容的比例 | 使用敏感词库扫描 + 轻量级分类模型自动拦截检测。 |

### 第 7 层：可观测层（能不能查）

| 指标 | 定义 | 备注 |
| :--- | :--- | :--- |
| **链路追踪覆盖率** | 请求带 TraceId 且完整链路可查 ÷ 总请求（目标 100%） | |
| **日志完整率** | 关键环节（入参、Prompt、SQL、结果）都有日志 ÷ 总请求 | |

## 二、 优先级排序（P0 先做，P2 有空再说）

| 优先级 | 指标分类 | 失败处理策略 | 理由与执行动作 |
| :--- | :--- | :--- | :--- |
| **P0 (一票否决)** | **安全**：越权拦截率、Data Scope 生效率、SQL 注入防护率 | **阻塞发布**，发现 1 例越权即阻塞上线，必须修复后重新跑通 | 上线前必须通过红队测试，发现 1 例越权即阻塞上线。 |
| **P0 (一票否决)** | **功能**：SQL 生成准确率、答案准确率、系统错误率 | **阻塞发布**，准确率低于阈值（如 85%）禁止发布 | 建立每日回归测试集，准确率低于阈值禁止发布。 |
| **P1 (核心关注)** | **性能/成本**：P90/P99 延迟、缓存命中率、单次问数成本、数据新鲜度达标率、单次成本告警阈值、月度预算上限 | **告警通知负责人**，允许带风险发布但需记录 TODO，后续迭代修复 | 压测报告必须包含环节耗时拆分，优化高耗时环节；实时监控数据时效性与成本红线。 |
| **P1 (核心关注)** | **可靠性**：拒答正确率、幻觉率（特别是数值幻觉）、降级成功率 | **告警通知负责人**，允许带风险发布但需记录 TODO | 重点测试"数值与数据库不一致"的幻觉场景。 |
| **P2 (体验优化)** | **体验/多轮**：多轮追问成功率、可解释性、审计完整率、回复内容合规率 | **记录到 Issue 跟踪**，不阻塞发布，产品灰度期通过用户反馈迭代优化 | 在产品灰度期通过用户反馈迭代优化。 |

## 三、 测试环境规范

大厂项目通常将测试环境分为三层，每层承担不同职责：

| 环境 | 位置 | 用途 | 特点 |
| :--- | :--- | :--- | :--- |
| **本地开发环境** | 开发者笔记本 | 单元测试、Prompt 调试、快速验证 | 轻量、快速、零成本，用 Mock 替代真实 LLM 调用 |
| **CI/CD 集成测试环境** | 服务器（容器化） | 集成测试、回归测试、自动化流水线 | 每次提交代码自动触发，连接真实 LLM API，跑完整评测集 |
| **预发布/灰度环境** | 服务器（与生产同构） | 性能压测、安全红队测试、全链路验证、**生产流量回放** | 配置与生产环境一致，使用脱敏后的真实数据 |

### 1. 本地开发环境

- **适用测试**：单元测试、Prompt 调试、Schema 幻觉检测
- **配置要求**：Python 3.10+，Docker Desktop，`.env` 文件配置 API Key
- **关键约束**：禁止直连生产数据库，使用本地 SQLite 或 Docker 化的测试数据库

### 2. CI/CD 集成测试环境

- **适用测试**：SQL 生成准确率、答案准确率、多轮对话回归、安全红队测试
- **配置要求**：Docker Compose 编排（应用 + 测试数据库 + Redis），通过 CI 平台 Secrets 注入 API Key
- **关键约束**：评测集规模控制在 200 条以内，单次回归测试成本不超过预算

### 3. 预发布/灰度环境

- **适用测试**：性能压测（P90/P99 延迟）、数据新鲜度验证、降级演练
- **配置要求**：与生产环境同构（相同规格的 GPU/CPU、相同版本的数据库），使用脱敏后的生产数据子集
- **关键约束**：压测流量需打标，确保不影响真实用户
- **生产流量回放（新增）**：支持将线上真实请求按 1%-5% 的比例异步重放到预发布环境，用于验证新版本在真实请求分布下的表现。回放流量需打标，结果不返回给用户，仅用于指标采集。

### 4. 环境切换与数据隔离

- 通过环境变量 `ENV=local|ci|staging|prod` 控制连接目标
- 测试数据库独立实例，禁止跨环境共享
- 所有环境的 API Key 通过密钥管理服务注入，禁止硬编码

### 环境隔离三原则

1. **数据隔离**：每个测试用例使用独立数据（唯一用户名、商品 ID 等），测试数据库独立实例，禁止跨环境共享。
2. **状态隔离**：每个用例执行前必须重置 Agent 状态（清空对话历史、重置工具调用计数、清空 memory），防止上下文污染。
3. **网络隔离**：本地单元测试使用 Mock 替代真实 API 调用；CI 环境仅允许访问测试 LLM API 和测试数据库；预发布环境可访问脱敏后的生产数据服务，但需流量打标。

## 五、 附录：评测集构建与 LLM-Judge 规范

### 1. 评测集构建标准

为了保证测试结果的客观性，评测集需包含以下三类数据：

- **线上日志采样 (60%)**：从生产环境脱敏后的真实用户提问，覆盖高频场景。
- **人工构造边界用例 (20%)**：包含模糊意图、超长文本、特殊符号、恶意攻击等边缘情况。
- **多轮对话剧本 (20%)**：构造包含"提问-追问-切换话题-澄清"的完整对话流。

### 2. LLM-Judge 校准

使用 LLM 评估 LLM 时，需进行校准以保证公平：

- **Prompt 模板**：提供明确的评分标准（如：SQL 逻辑等价得 1 分，字段错误扣 0.5 分）。
- **一致性测试**：使用一批已知结果的数据测试 Judge 模型，如果 Judge 的评分与人工评分一致性低于 80%，需调整 Judge Prompt。

### 3. 幻觉检测自动化方案

- **Schema 检查**：编写脚本解析生成的 SQL，提取所有表名和字段名，与数据库 `Information_Schema` 进行比对，不存在即为幻觉。
- **数值检查**：将 LLM 回答中的关键数字提取出来，与 SQL 执行结果的聚合值进行比对，误差超过 5% 视为数值幻觉。

### 4. SQL 逻辑等价判定补充说明

纯 LLM 文本比对存在误判风险（如 `A JOIN B` 与 `B JOIN A` 写法差异、子查询与 CTE 的等价改写等），因此引入**执行级逻辑验证**作为辅助手段：

1. 在测试库中分别执行"生成的 SQL"和"标准 SQL"。
2. 对比两个结果集是否一致（或高度重合，允许行顺序不同）。
3. 若结果集一致，则判定为逻辑正确；若不一致，再结合 LLM-Judge 进行二次分析，判断是"逻辑差异"还是"无害的写法差异"。

### 5. 评测集版本管理规范（新增）

为保证测试结果的可比性和可追溯性，评测集需遵循以下版本管理规范：

- **Git 管理**：评测集文件统一存放在 Git 仓库中，每次变更需提交 MR（Merge Request）并附带变更原因说明。
- **版本命名**：评测集文件命名需包含版本号，格式为 `eval_v{大版本}.{小版本}.json`（如 `eval_v2.3.json`），大版本升级表示评测集结构发生重大变更。
- **报告记录**：每次测试结果报告中必须记录所使用的评测集版本号，确保结果可追溯。
- **基线对比**：评测集版本升级时，需同时跑新旧两个版本的评测集，确认基线可比，避免因评测集变更导致"准确率下降"的误判。
- **变更审批**：评测集版本的大版本升级需经 Tech Lead 审批后方可合并，防止随意变更评测集导致指标波动。
