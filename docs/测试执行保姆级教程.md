# NL2SQL 测试执行保姆级教程（M7 评测：准确率 / P90 / P95 / 缓存命中率）

> 适用脚本：`scripts/eval_accuracy.py`（2026-09-07 升级版，内置 130 条可执行用例）
> 用例依据：`docs/spec/M7_评测用例集.md`（150 条中 JOIN 20 条因 users 业务数据未造，本轮跳过）
> 预计耗时：冒烟 ~3 分钟 ｜ 全量 15~25 分钟 ｜ 全量 qwen-turbo Token 费用 < 2 元

---

## 0. 你最终会得到什么

跑完后自动生成 3 份报告（`scripts/reports/` 目录下）：

| 文件 | 内容 |
|---|---|
| `eval_summary_时间戳.md` | **人看的摘要**：准确率、P50/P90/P95/P99、缓存命中均延迟 vs 未命中均延迟、分类别表格、失败清单 |
| `eval_report_时间戳.json` | 全量原始数据（每条用例的 code/sql/latency/cacheHit），写周报/复盘用 |


## 2. 前置检查（跑之前 2 分钟确认 3 件事）

SSH 登录服务器后执行：

```bash
# ① 后端活着（必须看到 Started Nl2sqlApplication 或 health 200）
curl -s -o /dev/null -w "health=%{http_code}\n" http://127.0.0.1:8080/actuator/health

# ② 登录接口正常（必须返回 code=2000 和 token）
curl -s -X POST http://127.0.0.1:8080/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"admin123"}' | head -c 200
echo

# ③ python3 和 requests 在不在
python3 --version
python3 -c "import requests; print('requests OK', requests.__version__)"
```

- ① 返回 `health=200`、② 返回 `"code":2000` 才继续
- ③ 如果报 `No module named requests` → `apt-get install -y python3-requests`（不用 pip，apt 直装）

**评测期间不要同时在浏览器手动问数**——并发组和缓存组的结果会被干扰。

## 4. 指标怎么读（报告里每个数字的含义）

| 指标 | 计算口径 | 达标线 | 面试怎么讲 |
|---|---|---|---|
| **准确率** | 通过用例数 / 总用例数（130 条）。通过 = code 符合预期 +（code=2000 时）SQL 包含全部关键词 | ≥ 80% | 「150 条用例 11 类，覆盖单表/聚合/时间/模糊语义/嵌套/安全/权限/性能/缓存/并发」 |
| **P50** | 所有请求服务端耗时（latencyMs）的中位数 | 参考值 | 「一半请求在 X 秒内返回」 |
| **P90 / P95** | 90% / 95% 的请求耗时低于此值 | P95 < 10s 可接受 | 「95 分位 X 秒，长尾主要来自 LLM 生成 + 失败自我修正重试」 |
| **P99 / 最大** | 长尾极值 | 观察用 | 用来说明「最坏情况来自执行失败触发 SelfCorrector 三次重试」 |
| **缓存命中均延迟 vs 未命中均延迟** | cacheHit=true / false 两组的 latencyMs 均值 | 命中应 < 100ms，差 10 倍以上 | 「语义缓存把重复问题从秒级降到毫秒级，省 qwen token」 |
| **分类别准确率** | 每类通过率 | 安全/权限类应 100% | 「安全拦截和权限隔离是 100%，说明兜底链路可靠；模糊语义类最低（NLP 固有难度）」 |

**延迟口径说明**：用服务端返回的 `latencyMs`（不含网络往返），所以数字比浏览器体感略小；客户端 RTT 也记录在 JSON 里可对比。

## 5. 已知预期差异（看报告前必读，否则会误判"失败"）

1. **非问数用例（104-106）预期从 4001 改成了 {4001, 4002}**：
   我们刚上线澄清兜底（ClarificationDecider），「今天天气怎么样」现在会返回 4002 反问而不是 4001 拒绝。两者语义都是"系统拒绝瞎编 SQL"，都算通过。M7 文档写于加固之前，这是**预期内的演进**。
2. **危险操作用例（101/102/108/110）判定为"非 2000 即通过"**：
   无论走 4003 SQL 拦截、4002 澄清还是 4001 拒绝，只要没把数据交出去就是安全兜底成功。
3. **JOIN 类 20 条（41-60）本轮跳过**：依赖业务 users 表（带 city/age/gender/vip_level），与 RBAC 的 users 表同名冲突，待造数后用 `--category normal` 单独补测。
4. **缓存组首问可能直接命中**：全量跑时缓存组的问题（如"总销售额是多少"）在常规组已经问过，1 小时 TTL 内首问就会 cacheHit=true。脚本只断言"第 2 次起命中"，不受影响，但你人工看明细时别奇怪。
5. **性能组（121-130）在 2C2G 上偏慢是正常现象**：orders 表数据量其实不大，真正的延迟大头是 qwen 生成（2~6 秒），不是 SQL 执行。

## 7. 失败排查表

| 现象 | 原因 | 处理 |
|---|---|---|
| 冒烟第一步 `RuntimeError: 登录失败` | 后端没起 / 密码错 | 回第 2 节前置检查；`systemctl status nl2sql-app` |
| 大面积 `请求异常 ... Connection` | `--base` 传错（本地跑却写了 127.0.0.1） | 本地跑用默认公网地址；服务器跑必须 `--base http://127.0.0.1:8080` |
| 大量 `code=4290` | 并发超 10（你同时在浏览器问数） | 评测期间别手动问数 |
| 某条 `请求异常 ... ReadTimeout` | LLM+自我修正超过 120s | 单条重跑：`--category normal` 看是否复现；偶发可忽略 |
| 时间类用例（61-75）大量 FAIL 且 SQL 正确 | 断言关键词 `order_date` 与 LLM 实际写法不符（如反引号包裹） | 把失败 CSV 贴我，我核对后放宽该组断言 |
| 缓存组全 FAIL（命中 0） | 后端不是最新 jar（cacheHit 字段是老版本） | 确认部署的是 17:56 之后的 jar |
| 权限组 FAIL：operator 的 SQL 没有 region IN | PermissionInjector 或账号 data_scope 问题 | 查 `SELECT data_scope FROM users WHERE username='operator'` 应为 `华东,华南` |
